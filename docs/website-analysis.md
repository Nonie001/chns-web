# วิเคราะห์แผนปรับปรุงเว็บไซต์ CHNS และแนวทางวางโครง Next.js

สถานะ: เอกสารวิเคราะห์ต้นทาง · 25 กันยายน 2569 · โครงโปรเจกต์ปัจจุบันดู [architecture.md](architecture.md)

## 1. ขอบเขตและข้อสรุป

เอกสารนี้วิเคราะห์ไฟล์ `CHNS_แผนปรับปรุงเว็บไซต์_2569.docx` (Revision Brief 01 วันที่ 26 สิงหาคม 2569) เทียบกับโปรเจกต์ก่อนเริ่มจัดโครง เพื่อเตรียมตัดสินใจเรื่องเนื้อหา เส้นทางผู้ใช้ และโครงสร้างไฟล์ Next.js เอกสารนี้เป็นภาพ ณ เวลาวิเคราะห์; โครงที่จัดจริงและสถานะหลังบ้านอยู่ใน [architecture.md](architecture.md)

ข้อสรุปหลัก: เว็บไซต์ควรมีแกนข้อมูลร่วมสำหรับ **ฝ่ายงาน 8 ฝ่าย, โครงการ/ภารกิจ, ข่าว/บทความ, รายงาน, ศูนย์ประสานงาน และองค์กรสมาชิก** แล้วแสดงข้อมูลชุดเดียวกันในหน้าแรก หน้ารวม และหน้ารายละเอียด เนื้อหาต้องผ่านการตรวจและอนุมัติก่อนเผยแพร่ โดยเฉพาะตัวเลขผลลัพธ์ ภาพบุคคล ข้อมูลติดต่อ และช่องทางรับบริจาค

> วิธีอ่าน: “ระบุในเอกสาร” หมายถึงข้อเสนอหรือข้อมูลจาก DOCX ซึ่งยังไม่ถือว่าได้รับอนุมัติให้เผยแพร่ ส่วน “ข้อเสนอทางเทคนิค” คือแนวทางที่เสนอสำหรับโปรเจกต์นี้ ไม่ใช่คำสั่งจาก DOCX และยังปรับได้ก่อนเริ่มพัฒนา ลิงก์ Drive/แบบฟอร์มใน DOCX เป็นแหล่งข้อมูลที่ต้องตรวจสิทธิ์และความถูกต้อง ไม่ใช่ข้อกำหนดให้เปิดเผยโดยอัตโนมัติ

## 2. สภาพโปรเจกต์ ณ เวลาวิเคราะห์

- เป็นโปรเจกต์เริ่มต้นของ Next.js **16.3.6**, React **19.2.8**, TypeScript และ Tailwind CSS 4 ใช้ App Router ที่โฟลเดอร์ `app/`
- หน้าแรกและ layout ยังเป็นค่าเริ่มต้น ไม่มีเนื้อหา CHNS, CMS, ฐานข้อมูล, ฟอร์ม หรือระบบบริจาค (ปัจจุบันย้ายเข้า `src/app/` แล้ว)
- `tsconfig.json` เปิด `strict` และมี alias `@/*` ไปที่รากโปรเจกต์อยู่แล้ว
- ณ เวลาตรวจเดิมยังไม่พบไฟล์เปลี่ยนแปลงที่ค้างใน Git

การวางโครงด้านล่างอิงคู่มือ **ที่ติดตั้งอยู่ใน `node_modules/next/dist/docs/`** โดยเฉพาะ `01-app/01-getting-started/02-project-structure.md`, `03-layouts-and-pages.md`, `06-fetching-data.md`, `14-metadata-and-og-images.md`, `15-route-handlers.md` และ `01-app/02-guides/internationalization.md` เพื่อให้สอดคล้องกับ Next.js รุ่นนี้

## 5. แนวทางสถาปัตยกรรมที่เสนอ

### หลักการ

1. **App Router สำหรับหน้าเว็บและ route handlers เฉพาะที่จำเป็น**: เก็บ `page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx` ตาม convention ของรุ่นที่ติดตั้ง; ไม่สร้าง API สำหรับการอ่านข้อมูลที่ Server Component อ่านจากแหล่งข้อมูลได้โดยตรง
2. **แยกเส้นทาง หน้าแสดงผล และแหล่งข้อมูล**: หน้า route เรียกฟังก์ชันอ่านข้อมูล; UI และ schema อยู่ในโมดูลที่เป็นเจ้าของงาน; เปลี่ยน CMS ในอนาคตได้โดยกระทบส่วนแสดงผลน้อย
3. **Server Components เป็นค่าเริ่มต้น**: ใช้ Client Components เมื่อมีปฏิสัมพันธ์จริง เช่น เมนูมือถือ ตัวกรอง แผนที่ หรือฟอร์ม; ตัดสินใจ cache/revalidation ของข่าวและตัวเลขตามความถี่การอัปเดต ไม่สมมติว่า fetch ถูก cache อัตโนมัติใน Next.js 16
4. **ข้อมูลมีสถานะการเผยแพร่**: `draft → review → approved/published → archived` พร้อมผู้รับผิดชอบ วันที่อัปเดต และสถานะสิทธิ์ภาพ/ไฟล์; CMS ที่เลือกต้องรองรับบทบาทและ workflow นี้
5. **เริ่มภาษาไทยและเตรียมเนื้อหาสองภาษา**: แยก field ตาม locale ใน schema ตั้งแต่แรก แต่ยังไม่กำหนด URL `/en` หรือ redirect ภาษาอัตโนมัติจนกว่าจะตรวจ URL เดิมและความพร้อมคำแปล
6. **ระบบการเงิน/ข้อมูลอ่อนไหวแยกขอบเขต**: หน้าโครงการและ CTA ทำได้ก่อน; การรับชำระเงิน, อัปโหลดหลักฐาน, ออกใบเสร็จ, จัดเก็บเอกสารสมัครสมาชิก ต้องมี workflow และมาตรการปฏิบัติจริงก่อนออกแบบ API

### โครงไฟล์เป้าหมาย

โครงที่จัดจริงใช้ `src/` และแยกพื้นที่เว็บสาธารณะกับหลังบ้านตาม [architecture.md](architecture.md) ซึ่งเป็นแหล่งอ้างอิงปัจจุบันสำหรับ route และตำแหน่งไฟล์ ส่วนการวิเคราะห์นี้ใช้ประกอบการตัดสินใจเรื่องขอบเขตและข้อมูลจากเอกสารต้นทาง

| Article | id, slug, ประเภท, วันเผยแพร่, วันกิจกรรม, ฝ่าย, พื้นที่, projectIds, tagIds, ภาพ/alt, เนื้อหา, แหล่งข่าว | รองรับข่าว บทความ รายงานภารกิจ และวิดีโอโดยไม่ต้องซ้ำข้อมูลโครงการ |
| Report | id, ชื่อ, ปี, ประเภท, file/URL, เจ้าของข้อมูล, publishStatus | ตรวจสิทธิ์เผยแพร่ PDF ก่อนเปิดให้ดาวน์โหลด |
| Center | id, ระดับ, ภูมิภาค/จังหวัด, พื้นที่รับผิดชอบ, contact, publishStatus | แยกข้อมูลผู้ประสานงานส่วนตัวจากข้อมูลสาธารณะ |
| MemberOrganization | id, ชื่อ, โลโก้, URL, permissionStatus | เอกสารเสนอให้แสดงโลโก้เป็นหลัก |
| SiteSettings | ช่องทางติดต่อ, social, navigation, emergencyBanner, donationMethods | แก้ข้อมูลกลางครั้งเดียวแล้วใช้ทุกหน้า |

ทุก entity ที่แสดงบนเว็บควรมี `createdAt`, `updatedAt`, `publishedAt`, locale, ผู้ตรวจ/ผู้อนุมัติ และข้อมูลสิทธิ์สื่อเท่าที่เกี่ยวข้อง กำหนด taxonomy กลางอย่างน้อย **ฝ่าย, ประเภทภารกิจ, จังหวัด/ประเทศ, ปี, โครงการ** ตามเอกสาร

## 6. ลำดับทำงานที่เสนอ

ลำดับใน DOCX มี 5 phase; สำหรับโปรเจกต์นี้ควรใช้เป็น **กรอบวางแผน** และมีเงื่อนไขก่อนเริ่มแต่ละช่วง:

1. **ตรวจข้อมูลและ URL เดิม**: ยืนยันชื่อหน่วยงาน/ฝ่าย ข้อมูลติดต่อ ประวัติ รายการ URL เก่า สิทธิ์รูป และเนื้อหาที่ผิด/ว่าง; ทำ redirect map
2. **โครงหลักและเนื้อหา**: design system, หน้าแรก, เกี่ยวกับเรา, ฝ่าย 8 ฝ่าย, โครงการ, ข่าว, ติดต่อ; ตั้ง CMS พร้อมบทบาทผู้ดูแลและแม่แบบเนื้อหา
3. **เครือข่ายและความโปร่งใส**: ศูนย์ประสานงาน องค์กรสมาชิก รายงาน และการอ้างอิงตัวเลขผลลัพธ์
4. **การมีส่วนร่วมและการวัดผล**: เส้นทางสนับสนุน/สมัครสมาชิกที่มีขั้นตอนอนุมัติชัด, analytics event และ SEO/redirect ตรวจจริง
5. **ส่วนขยาย**: ภาษาอังกฤษ แผนที่โต้ตอบ ตัวกรองขั้นสูง dashboard เมื่อข้อมูลพร้อม

ก่อนเผยแพร่แต่ละหน้า ควรตรวจบนมือถือและคีย์บอร์ด, title/description/OG/alt, ลิงก์และ redirect, วันที่/แหล่งของตัวเลข, สิทธิ์ภาพ และการอนุมัติจากเจ้าของข้อมูล ฟอร์มต้องทดสอบ validation, การจำกัดไฟล์, การเข้าถึงข้อมูลและการแจ้งผลหลังส่งด้วย

## 7. คำถามที่ควรตอบก่อนเริ่มเขียนเว็บ

1. **เว็บเดิมอยู่ URL ใด และเข้าถึงรายการหน้า/analytics ได้หรือไม่?** สิ่งนี้กำหนด URL ใหม่และ 301 redirect
2. **ใครเป็นผู้อนุมัติเนื้อหาและสื่อของแต่ละฝ่าย?** รวมถึงประวัติปี 2557/2015, ชื่อฝ่าย, รายชื่อผู้บริหาร และข้อมูลศูนย์
3. **รอบแรกต้องการภาษาอังกฤษจริงหรือเพียงเตรียมโครง?** หากต้องมี EN ต้องจัดเจ้าของคำแปลและเกณฑ์ไม่เผยแพร่หน้าที่ยังแปลไม่ครบ
4. **CMS ใครจะใช้และ workflow อนุมัติเป็นอย่างไร?** จำนวนผู้ใช้ บทบาท งบประมาณ และความต้องการ host มีผลต่อการเลือก CMS
5. **“ร่วมสนับสนุน” หมายถึงวิธีใดในรอบแรก?** แสดงบัญชี/QR ที่อนุมัติ, ลิงก์ภายนอก หรือรับชำระเงินบนเว็บ; ใครตรวจยอดและออกใบเสร็จ
6. **ฟอร์มสมัครสมาชิกต้องส่งเข้าใครและเก็บเอกสารที่ใด?** รวมข้อกำหนด PDPA, ระยะเวลาเก็บ และเลขอ้างอิง
7. **มีชุดแบรนด์ที่อนุมัติหรือไม่?** โลโก้ สี ฟอนต์ ภาพ และแนวทางใช้ภาพผู้รับความช่วยเหลือ

เมื่อได้คำตอบเหล่านี้ จึงทำ sitemap/URL mapping ฉบับยืนยัน, เลือก CMS และจัด backlog รายหน้าได้โดยไม่ต้องรื้อโครงใหญ่ภายหลัง
